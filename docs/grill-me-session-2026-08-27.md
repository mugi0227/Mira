# Mira Grill-Me Session — 2026-08-27

この文書は、2026-08-27に追加で行ったGrill-Meのライブ意思決定記録。セッション完了後、`grill-me-decisions.md` と `requirements-specification.md` の正本へ統合する。

## Q61 — 断り文句ジェネレーター

**決定: C + AI生成 + ガチャ式再生成。**

- 誘いを断る文章をAIで生成する。
- 相手との関係、誘いの内容、断る強さ等を文脈として利用する。
- 嘘の理由は作らない。
- `これ使う` / `もう一個` / `もう少し柔らかく` 等で再生成できる。
- AI非対応環境ではテンプレート組み合わせへフォールバックする。

## Q62 — 余白量を自分で決められない人へのおまかせ

**決定: Miraのおまかせを基本にし、余白量を「少なめ / ふつう / 多め」で調整できる。**

- 既存の確定予定と負荷を見て、その月に必要な余白量をMiraが自動計算する。
- 固定の「休息4日」等ではなく、月の負荷に応じて推奨量を変える。
- ユーザーはおまかせ強度を `少なめ / ふつう / 多め` から選べる。
- 予定の追加・削除で必要余白が変わった場合、再提案する。

## Q63 — Miraによる候補日の自動選定

**決定: Miraが候補を自動選定し、最初から複数候補を表示する。**

- 自分の予定だけでなく、日程調整にも適用する。
- 第一候補は「いちばんおすすめ」として強調する。
- 第二・第三候補等も、ボタンを押さなくても最初から表示する。
- ユーザーは候補を削除・追加・入れ替えできる。

## Q64 — 日程調整の時間粒度

**決定: 朝・昼・夜を基本粒度とし、複数選択可能。終日も選べる。詳細時刻は必要なときだけ開く。**

- 1〜2時間程度の予定: 朝 / 昼 / 夜から複数選択。
- 半日程度の予定: 午前 / 午後を中心に選択。
- 終日予定: 終日を選択。
- 必要な場合のみ「時間を細かく指定」で時刻単位へ進む。
- Mira内部では具体的な時間帯を仮定して負荷・重複判定を行える。

## Q65 — 自動提示する候補数

**決定: D。基本3候補、良い候補が少なければ2、選択肢が十分あれば最大5程度までMiraが調整する。**

- 数合わせで悪い候補を出さない。
- 日程調整では、相手へそのまま送れる候補集合を最初から作る。

## Q66 — 雑入力の入口

**決定: B。ただし一発コマンドではなく、軽い会話を継続できる。**

ホームにMiraへ雑に投げられる入口を1つ置く。

入力例:

- `9/12これ誘われたわ、いけそう？`
- `これ誘われた。いついけそう？`
- `来月みらのとどっかで遊びたい`
- `美容院そろそろ行きたい`
- `この誘い断りたい`

基本はAIが意図を判定し、以下のようなMira内部の処理へ振り分ける。

- 予定追加
- 参加可能性確認
- 日程調整
- 候補日探索
- 断り文生成

AIの確信が低い場合だけ、`行けそうか見る / 別の日を探す / 予定に入れる` のような少数選択肢で確認する。

### 会話継続

一度の入力で完結させることを基本とするが、同じ案件について簡単に会話を続けられる。

例:

1. `来週友達と焼肉行きたい`
2. Mira: 候補を3件提示
3. `夜は無理`
4. Mira: 直前の案件を引き継いで候補を再計算
5. `じゃあ土曜昼の3つで送る文作って`
6. Mira: 同じ案件の候補を使って共有文を生成

### AIの責務

Foundation Modelsにエージェンティックな全処理を任せない。

AIは主に、ユーザーの雑な自然言語を構造化する。

例:

- intent
- title
- people
- date/date range
- duration
- allowed time bands
- explicit constraints
- requested action

その後の以下は決定論的なMiraロジックで処理する。

- 空き判定
- 基本時間
- 余白との衝突
- 予定負荷
- 月間目標
- 候補ランキング
- 最終防衛
- 保存・更新

**原則: 会話UIは入口であり、判断エンジンそのものではない。**

## Q67 — 会話文脈の保持単位

**決定: B。会話は案件ごとに保持する。ただしユーザーにチャット一覧を管理させない。**

- 日程調整、検討中の誘い、予定相談などは裏側で「案件コンテキスト」として保持する。
- 数日後でも同じ案件へ戻り、条件追加や変更を会話で続けられる。
- `調整` タブはチャット一覧ではなく、進行中案件の管理画面として扱う。
- 確定後の予定についても後から話題にできる必要があるため、検索対象を「調整中 / 検討中」だけに限定しない。
- 会話履歴そのものより、タイトル・状態・条件・候補・関連予定ID等の構造化された案件状態を正として保持する。

## Q68 — 「焼肉の件」等の案件特定方法

**決定: C。Harnessが毎回必ず自動検索し、高確度なら自動選択、曖昧なら候補提示。手動の案件指定も常に可能にする。**

### 自動経路

雑入力が送信されたら、Foundation Modelへ丸投げする前にアプリ側のHarnessが必ずローカル検索を行う。

検索対象候補:

- 日程調整案件
- 検討中の誘い
- 確定済み予定
- 下書き / 最近終了した案件

検索結果を少数件へ絞ったうえで、Foundation Modelには以下を渡す。

- ユーザーの現在発話
- 検索で絞った候補コンテキスト
- 必要最小限の直近会話

Foundation Modelの役割は、`どの案件を指しているか` と `何を変更・質問しているか` の構造化解釈に限定する。

### 確信度別UX

- 高確度: 自動で案件を選択し、そのまま処理する。
- 中程度: `この焼肉のこと？` のように候補を1〜3件提示する。
- 低確度 / 該当なし: 新規案件として扱うか、最小限の確認を行う。

### 手動指定

チャット入力欄の横に「この話について」を指定できるボタンを置く。

押すと、ユーザー自身が案件・予定を検索して選択できる。

選択後は入力欄の近くに `友達と焼肉 ×` のようなコンテキストチップを表示し、そのコンテキストを固定して会話できる。

**原則: 自動検索を理想経路、手動指定を信頼できる逃げ道として両立する。AIに検索そのものを任せない。**

## Q69 — 過去予定の検索範囲と検索速度

**決定: 通常の会話検索では過去予定を検索しない。過去は手動検索で明示的に有効化した場合だけ検索する。検索は速度を最優先する。**

### 理由

- `焼肉の件` 等の通常会話で参照したい対象は、進行中・検討中・未来予定である頻度が高い。
- 過去予定を常時混ぜると検索ノイズが増え、自動特定の精度と速度を落とす可能性が高い。
- 過去予定を参照したいニーズはあるが頻度が低いため、明示操作へ分離する。

### 通常の自動検索対象

- 日程調整中の案件
- 検討中の誘い
- 下書き
- 未来の確定予定
- 現在進行中とみなせる予定・案件

### 通常の自動検索から除外

- 終了済みの過去予定
- 完了済みの過去調整
- 古いアーカイブ

### 手動検索

- 入力欄横の `この話について` から検索窓を開く。
- 初期状態では現在・未来のみを検索する。
- `過去も検索` を明示的にON / タップした場合だけ、過去予定・完了済み案件まで検索範囲を広げる。

### 速度方針

- 通常検索の初段にLLMを入れない。
- ネットワークを必要としないローカル検索を先に行う。
- 現在・未来の小さい検索集合を優先する。
- 少数候補へ絞ってからFoundation Modelへ渡す。
- Foundation Modelの応答待ちを、検索結果表示そのものの待ち時間にしない。

**原則: 普段は速く・狭く検索し、過去探索はユーザーが求めたときだけ広げる。**

## 日程調整UIの方向性（継続検討）

日程調整は専用の複雑なフォームだけに閉じず、メインの月間カレンダー自体を候補選択UIとして利用する方向を検討する。

案:

1. タイトルと所要時間を入力。
2. 所要時間に応じた時間帯を複数選択。
3. 月間カレンダーの各日に、該当時間帯を表すシンプルなアイコンボタンを表示。
4. Miraが自動選定したおすすめ候補を最初から選択・強調。
5. ユーザーはカレンダー上で候補を追加・削除できる。
6. `この候補でOK` で調整案件を作成。
7. 共有文を生成し、候補を仮押さえする。

この方向では、`調整` タブは新規調整の作成場所というより、進行中・検討中の案件を管理する場所へ寄せられる可能性がある。
