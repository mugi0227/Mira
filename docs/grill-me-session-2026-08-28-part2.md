## Q73 — 仮条件生成後の遷移

**決定: B。仮条件が作れたら確認画面を挟まず、そのまま月間カレンダーを日程調整モードへ切り替え、Miraのおすすめ候補まで即表示する。**

### UX

例えば、

> `来月友達と焼肉行きたい`

からMiraが、

- 所要時間: `1〜2時間`
- 時間帯: `夜`

を仮定できた場合、`この条件で探す？` のような確認画面は挟まない。

そのまま月間カレンダーを日程調整モードへ切り替え、Miraが選んだ2〜5件の候補を最初から表示・選択状態にする。

画面上部には、

- `1〜2時間 ×`
- `夜 ×`

のような仮条件チップを残す。

ユーザーがチップを修正した場合は候補を即再計算する。

### 理由

- 雑入力からフォーム確認へ戻ると入力負荷削減の価値が弱くなる。
- Miraが仮入力した内容はチップで可視化されているため、確認画面を別途挟まなくても修正可能。
- 理想体験は「入力 → 即、候補が載ったカレンダー」であり、人間は間違っている部分だけ直す。

**原則: まず動かして見せる。確認のためだけの画面遷移は増やさない。**

## Q74 — 調整モード中の時間帯ボタン表示

**決定: C。選択対象の時間帯ボタンを全日表示し、おすすめ・通常候補・衝突ありを視覚的に区別する。衝突候補も完全には禁止しない。**

### 表示状態

日程調整モードでは、所要時間と選択中の時間帯に応じた小さな時間帯ボタンを各日セルへ表示する。

例: `1〜2時間` + `昼 / 夜` の場合、各日に昼・夜の2ボタンを表示する。

状態は最低限以下へ分ける。

- **Miraおすすめ**: 強く強調し、初期候補として選択済みにできる。
- **通常選択可能**: 控えめに表示し、タップで候補へ追加できる。
- **衝突あり / 非推奨**: さらに薄く表示し、警告アイコン等で理由があることを示す。
- **選択済み**: おすすめか手動追加かにかかわらず、明確な選択状態を示す。

### 衝突候補

以下と重なる場合も、ボタン自体を完全に消したり選択不能にしない。

- 基本的に予定を入れない時間
- 守っている余白
- 確定予定
- 別の日程調整候補

タップ時に、

1. 何と重なるかを表示する。
2. 可能ならより良い代替候補を示す。
3. それでも使いたい場合は明示確認のうえ候補へ追加できる。

### 理由

- 不可能な候補を隠すと、ユーザーが「なぜそこを選べないか」を理解できない。
- 現実には例外的に重複を許容したい場合がある。
- Miraの「禁止する管理者ではなく、影響を示す秘書」という原則と一致する。
- 月間カレンダー上で候補の全体像を一度に把握できる。

**原則: 良い候補は光らせる。悪い候補は理由付きで薄く残す。最終判断は本人に残す。**

## Q75 — Miraおすすめ候補の初期選択状態

**決定: B。Miraがおすすめした候補は最初からすべて選択済みにする。ただし `おすすめをすべて外す` 一括解除を用意する。**

### UX

Miraが例えば3候補をおすすめした場合、ユーザーが1件ずつ選択するのではなく、最初から候補集合として選択済みにする。

例:

- `10/10(土) 夜` — おすすめ / 選択済み
- `10/16(金) 夜` — おすすめ / 選択済み
- `10/24(土) 夜` — おすすめ / 選択済み

ユーザーは、

- 不要な候補だけ個別に外す
- 別の日・時間帯を追加する
- `おすすめをすべて外す` で自動選択分を一括解除する

ことができる。

一括解除後もMiraのおすすめ表示自体は残してよいが、候補としての選択状態は解除する。

### 理由

- Miraの価値は候補を探す作業そのものを肩代わりすることにある。
- ユーザー操作を「ゼロから候補を選ぶ」から「Miraの案を添削する」へ変えられる。
- 一括解除を用意することで、自動選択を押し付けられている感覚を避けられる。

**原則: おすすめは完成案としてまず置く。本人は必要なところだけ直せる。**

## Q76 — 粗い時間帯候補の内部表現

**決定: C。候補段階では、正確な開始・終了時刻へ仮固定せず、`時間帯 + 所要時間` の組み合わせとして保持する。**

例:

- `9/10 夜 + 1〜2時間`
- `9/14 午後 + 半日`

### 判定

- 同じ日・同じ時間帯を使う別候補がある場合は、正確な時刻が未確定でも競合候補として警告する。
- 予定負荷は時間帯全体の長さではなく、予定の所要時間を基準に計算する。
- `夜` を選んだからといって、18:00〜24:00の6時間予定として扱わない。
- 正確な開始・終了時刻は、相手との調整後・予定確定時など必要になった時点で決められる。

### データ設計原則

`timeBand` と `durationBucket` を別フィールドとして保持し、候補段階で具体的な `DateInterval` へ潰さない。

詳細時刻が明示された場合だけ、具体的な開始・終了時刻を併記する。

**原則: 候補探索では生活上の幅を保ち、必要になるまで偽の精密さを持ち込まない。**
